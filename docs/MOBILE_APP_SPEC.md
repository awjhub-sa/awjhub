## ٢. الأدوار والدخول

مصدر المنطق: [`src/context/AuthContext.jsx`](../src/context/AuthContext.jsx)

### آلية الدخول الحالية

```
المستخدم يدخل رقم هوية (١٠ أرقام)
  → بحث في users.id_number
  → التحقق أن role ∈ {observer, supervisor}
  → التحقق أن الدور يطابق التبويب المختار
  → حفظ صف المستخدم كاملاً في localStorage تحت moraqeb_monitor_session_v1
```

لا كلمة مرور، ولا رمز تحقق، ولا Supabase Auth. المسؤول والموظف فقط يستخدمان
بريداً وكلمة مرور عبر `supabase.auth`.

> ### 🔴 هذه ليست مصادقة
>
> رقم الهوية **معرِّف لا سرّ**. من يعرف رقم هوية أي مراقب يدخل باسمه ويرسل
> تقييمات ووجبات وبلاغات منسوبة إليه.
>
> على الويب كان الأثر محدوداً (رابط داخلي). أما تطبيق منشور على المتاجر فيصبح
> الهجوم متاحاً لأي شخص حمّل التطبيق. **يجب معالجة هذا قبل النشر** — انظر
> §٧ الميزة رقم ١.

### الفرق بين الدورين في البيانات

| | المراقب | المشرف |
|---|---|---|
| الحقل | `users.center` — مركز واحد نصاً | `users.assigned_centers` — مصفوفة |
| النطاق | مركزه فقط | كل مراكزه، مع محدّد مركز نشط |
| الشاشات | تعبئة | تعبئة + متابعة إنجاز المراقبين |

المشرف يقرأ مراكزه من `users.assigned_centers` ويرتّبها رقمياً
([`SupervisorHome.jsx:355`](../src/pages/Supervisor/SupervisorHome.jsx#L355))،
ثم يشترك في مستمعات عبر **كل** مراكزه لبناء لوحته الموحّدة.

## ٣. الجداول التي يلمسها التطبيق

من [`src/lib/db.js`](../src/lib/db.js). الطبقة تحوّل camelCase ↔ snake_case
تلقائياً، فالتطبيق يكتب `scoreOutOf10` وتصل `score_out_of10`.

| الجدول | قراءة | كتابة | ملاحظة |
|---|---|---|---|
| `users` | ✅ | — | الدخول وبيانات الملف |
| `assigned_tasks` | ✅ realtime | — | المهام الموكلة للمركز |
| `task_completions` | ✅ realtime | ✅ | سجل التسليم |
| `meal_evaluations` | ✅ | ✅ | ٣٥ سؤالاً + الدرجة |
| `mina_readiness` | ✅ | ✅ | ٢٦ بنداً |
| `arafat_readiness` | ✅ | ✅ | ٢٤ بنداً |
| `meal_phases` | ✅ realtime | ✅ upsert | صور المراحل |
| `reports` | ✅ | ✅ | بلاغات طارئة |
| `logistics_requests` | ✅ | ✅ | طلبات إسناد |

**مفتاح `meal_phases` مركّب نصياً**: `` `${center}_d${day}_${mealType}` `` —
مثل `مركز 40_d8_lunch`. يضمن صفاً واحداً لكل (مركز، يوم، وجبة).

### أرقام تلقائية

`reports.report_number` و `logistics_requests.request_number` تُولَّد في قاعدة
البيانات عبر `nextval()` بصيغة `BLG-0001` و `ISN-0001`. **لا يولّدها التطبيق** —
يقرأها من الصف المُرجَع بعد الإدراج.

### تتبّع الحالة

[`src/lib/statusTracking.js`](../src/lib/statusTracking.js) — كل بلاغ وطلب يحمل:

```
status       الحالة الحالية
statusSince  متى دخلها
durations    { pending: ms, in_progress: ms, ... }  تراكمي لكل حالة
closedAt     وقت الإغلاق (للحالات النهائية فقط)
```

الحالات النهائية: البلاغ `resolved`، الإسناد `delivered` أو `rejected`.
التطبيق يكتب `initialStatusFields('pending')` عند الإنشاء فقط؛ التحديث من
لوحة الإدارة.

## ٤. الشاشات — التدفق والحقول

### ٤٫١ الرئيسية (`/home`)

ثلاثة تبويبات سفلية: **الإجراءات** / **المنيو** / **النشاط**.

- **الإجراءات** — بطاقات تنقّل بشارات عدّ: تقييم الوجبات، جاهزية منى، جاهزية
  عرفة، بلاغ طارئ، طلب إسناد. الشارات محسوبة من `assigned_tasks` ناقص
  `task_completions`.
- **المنيو** — منيو اليوم حسب جنسية المركز من [`config/menus.js`](../src/config/menus.js).
- **النشاط** — تغذية حيّة من ٥ جداول عبر اشتراكات realtime، مصفّاة على
  `center` ومقيّدة بسجلات اليوم.

### ٤٫٢ تقييم الوجبات (`/mealcheck`) — أعقد شاشة

**مرحلتان متتاليتان: صور المراحل ← ثم الأسئلة.**

**أ. المراحل** — [`Mealcheck.jsx:30`](../src/pages/Mealcheck.jsx#L30)

```
1  مرحلة التجهيز
2  مرحلة الطبخ          ← تُحذف للوجبة الجافة
3  مرحلة التعبئة والتوزيع
```

`buildPhases(categories)`: إذا كانت `meal_categories === ['dry']` بالضبط
(جافة فقط) → مرحلتان. أي حالة أخرى (مطبوخة، معقمة، مختلطة، أو غير محددة) →
ثلاث مراحل.

> **فخّ في الترقيم**: الجاف يستخدم المعرِّفين `1` و `3`. رقم الخطوة المعروض
> يجب أن يكون `idx + 1` لا `phase.id`، وفحص الفتح `phaseDone[phases[idx-1].id]`
> لا `phaseDone[idx]`. الخلط هنا يقفل المرحلة الثالثة على الوجبة الجافة.

كل مرحلة: صورة إلزامية → ضغط → رفع إلى `phases` bucket → `upsert` في
`meal_phases` مع ختم زمني `phase1|2|3` ورابط الصورة و uid.

**ب. الأسئلة** — [`config/mealQuestions.js`](../src/config/mealQuestions.js)

**٣٥ سؤالاً** في ٦ أقسام: متطلبات عامة (٩)، التخزين (٣)، العاملين (٥)،
التشغيل (٥)، الجودة (٨)، التوزيع (٥).

خصائص السؤال:

| الحقل | المعنى |
|---|---|
| `score` | 0.25 / 0.50 / 1.00 — و **`0` = استرشادي لا يُحتسب** |
| `negative` | الإجابة «لا» هي التي تمنح الدرجة (مثل «هل توجد آثار فئران؟») |
| `requiresPhoto` | صورة إلزامية عند الإجابة — ١١ سؤالاً |
| `note` | ملاحظة توضيحية تحت السؤال |

ثلاثة أسئلة استرشادية (`score: 0`): رقم 3، 10، 30.

`MEAL_MAX_SCORE` يُحسب من المجموع لا يُكتب يدوياً، و `computeMealScore(answers)`
تمنح الدرجة عند مطابقة `negative ? 'لا' : 'نعم'`.

**ج. الحفظ** — سجلان في معاملة منطقية واحدة:

```
meal_evaluations ← uid, center, caterer, observer, answers{...__photos},
                   totalScore, maxScore, scoreOutOf10, percentage,
                   mealType, scheduledDate, timestamp
task_completions ← taskId, taskType:'meal_evaluation', mealType,
                   scheduledDate, center, uid, observerName, timestamp
```

**د. المسودة** — تُحفظ في `localStorage` تحت
`` `mealcheck_${uid}_${taskId}_${mealType}` `` عند كل تغيير، وتُستعاد عند
العودة. **هذه الشاشة الوحيدة التي تحفظ مسودة.**

### ٤٫٣ جاهزية منى وعرفة

| | منى | عرفة |
|---|---|---|
| البنود | ٢٦ (المعرّف ٤ محذوف) | ٢٤ (متصلة ١–٢٤) |
| الملف | [`minaQuestions.js`](../src/config/minaQuestions.js) | [`arafatQuestions.js`](../src/config/arafatQuestions.js) |

أنواع البنود: `yesno`، `yesno_detail`، `choice`، و `yesno_multi_detail`
(خاص بعرفة — سؤال الثلاجات والترامس).

الدرجات: 0.25 / 0.50 / 0.75 / 1 / 2، و `null` للاسترشادي.
[`computeReadinessTotals`](../src/config/readinessScore.js) تتجاهل غير الرقمي
وغير الموجب، وتُطبّع على ١٠.

**التفاصيل والصور تُدفن داخل `answers`** لا في أعمدة منفصلة:

```js
answers: { ...answers, __details: details, __photos: photos }
```

> ⚠️ `__details` و `__photos` مفتاحان محجوزان. أي بند رقمه `__details` سيصطدم.

### ٤٫٤ بلاغ طارئ (`/report`)

- **٢٦ نوع بلاغ** معرّفة في الصفحة نفسها مع درجة خطورة مسبقة
  (`high` / `medium` / `low`) تُضبط تلقائياً عند اختيار النوع
- المشعر: منى / عرفات — والوجبة: إفطار / غداء / عشاء
- **صورة وفيديو كلاهما إلزامي** — يُرفعان بالتوازي إلى `reports` bucket تحت
  `` `${center}/${timestamp}/` ``
- الصورة تُضغط قبل الرفع، الفيديو **لا**

### ٤٫٥ طلب إسناد (`/logistics`)

- الفئة: `meals` إسناد وجبات / `water` إسناد مياه
- نوع الدعم: `internal` / `external` / `both`
- الكميات مشروطة بنوع الدعم:

```
internal → qtyInternal ≥ 1
external → qtyExternal ≥ 1
both     → كلاهما ≥ 1
```

- الأرقام العربية (٠–٩) تُحوَّل للاتينية قبل التحقق —
  [`LogisticsRequest.jsx:111`](../src/pages/LogisticsRequest.jsx#L111)

### ٤٫٦ شاشة المشرف الرئيسية

الأعقد على الإطلاق (١١٠٨ سطر). تفتح مستمعات realtime عبر **كل** مراكز المشرف
في آنٍ واحد لتغذية: قائمة المهام المعلّقة، بطاقات الإحصاء، جرس الإشعارات،
والبلاغات والطلبات المفتوحة.

عند اختيار مركز، تُمرَّر هويته عبر `location.state.centerId` إلى شاشات
`Sup*` — التي هي نسخ من شاشات المراقب تكتب `role: 'supervisor'` إضافياً.

## ٦. التخزين والرفع

مخزنان في Supabase Storage:

| Bucket | المحتوى | المسار |
|---|---|---|
| `phases` | صور مراحل التحضير وصور الأسئلة | `mealcheck/{center}/{date}/{meal}/q{id}_{ts}.jpg` |
| `reports` | صور وفيديوهات البلاغات | `{center}/{ts}/image_*` و `video_*` |

> **قيد مهم**: Supabase Storage يرفض المفاتيح التي تحوي أحرفاً غير ASCII أو
> مسافات. أسماء المراكز عربية («مركز 40»)، لذا يمرّ كل مسار على
> `sanitizeStoragePath()` في [`db.js:202`](../src/lib/db.js#L202) الذي يستبدل
> كل ما ليس `[\w./-]` بشرطة سفلية. **أي تطبيق جديد يجب أن ينقل هذه الدالة
> حرفياً** وإلا فشل الرفع لكل مركز.

## ٧. ميزات مقترحة — مرتّبة بالأثر

### ١. مصادقة حقيقية 🔴 حرجة

الوضع الحالي (رقم هوية بلا سرّ) غير مقبول لتطبيق منشور. الخيارات تصاعدياً:

- **رمز تحقق برسالة** على جوال المستخدم — الأرقام موجودة أصلاً في
  `users.phone` (٧٤ من ٧٦ مستخدماً لديهم رقم)
- **ربط الجهاز**: أول دخول يسجّل بصمة الجهاز، وأي جهاز جديد يحتاج موافقة مسؤول
- **قفل حيوي** (بصمة/وجه) لفتح التطبيق بعد أول دخول

الأخف تنفيذاً والأعلى مردوداً: رمز التحقق + قفل حيوي.

### ٢. طابور عمل دون اتصال 🔴 حرجة للميدان

منى وعرفة معروفتان بضعف التغطية وقت الذروة. اليوم كل إدراج ورفع يتطلب اتصالاً،
وفشل الرفع **يضيّع النموذج كاملاً**.

المطلوب:
- حفظ النموذج محلياً فور الإرسال، ثم مزامنة في الخلفية
- طابور رفع للصور والفيديو مع إعادة محاولة تصاعدية
- مؤشّر واضح: «٣ نماذج بانتظار المزامنة»

هذه الميزة وحدها تبرّر الانتقال للتطبيق.

### ٣. حفظ المسودة في كل النماذج

`Mealcheck` وحدها تحفظ مسودة. نموذج جاهزية عرفة **٢٤ بنداً** بتفاصيل وصور —
مكالمة واردة تمسحه بالكامل. عمّم آلية `localStorage` الموجودة على كل النماذج.

### ٤. إشعارات فورية

اليوم الإشعارات realtime تعمل **فقط والتطبيق مفتوح**. إشعار فوري عند إسناد
مهمة جديدة أو تحديث حالة بلاغ يغيّر سرعة الاستجابة الميدانية جذرياً.

### ٥. ختم موقع على الإرسال

إرفاق إحداثيات GPS مع كل تقييم يثبت أن المراقب كان في المركز فعلاً. قيمة
تدقيقية عالية، وتنفيذها سطران.

### ٦. كاميرا مباشرة بدل منتقي الملفات

الويب يفتح منتقي ملفات؛ التطبيق يفتح الكاميرا مباشرة، ويقدر يضيف علامة مائية
بالوقت والمركز على الصورة — دليل أقوى وأصعب تزويراً.

### ٧. تقليل أخطاء اختيار المركز

المشرف يتنقّل بين مراكز كثيرة. رمز QR على لوحة كل مركز يختار المركز الصحيح
بمسحة واحدة بدل قائمة طويلة.

### ٨. وضع «مهامي اليوم»

شاشة واحدة تجمع كل ما هو مطلوب اليوم عبر كل المراكز مرتّباً بالأولوية، بدل
التنقّل بين خمس شاشات.

## ٨. React Native أم Flutter؟

### التوصية: **React Native + Expo**

والسبب ليس تفضيلاً تقنياً مجرّداً، بل حساب ملموس:

**١. ~٢٬٤٦٣ سطراً تنتقل بلا سطر واحد معاد كتابته.**

جدول §٥ كله JavaScript خالص: بنوك الأسئلة، دوال الاحتساب، المنيو (١٤٠٨ سطر)،
المراكز، الجنسيات، حساب مدد الحالات، طبقة `db.js`. مع React Native تُنسخ
كما هي. مع Flutter **تُعاد كتابتها كلها بلغة Dart**.

وإعادة كتابة ١٤٠٨ سطر من بيانات المنيو ليست ترجمة ميكانيكية — كل خطأ نسخ فيها
يصبح وجبة خاطئة تظهر لمراقب في الميدان.

**٢. `supabase-js` يعمل في React Native مباشرة**، بما فيه realtime والتخزين.
Flutter له `supabase_flutter` وهو جيد، لكنه مسار مختلف يحتاج إعادة كتابة
`db.js` وطبقة التحويل camelCase ↔ snake_case ومنطق الاشتراكات.

**٣. مصدر واحد للحقيقة.** حين تُعدَّل درجة سؤال أو يُضاف مركز، تعدّله مرة
واحدة ويسري على الويب والتطبيق. مع Flutter تعدّله مرتين — وستنسى المرة الثانية
يوماً ما.

**٤. خبرتك.** الكود الحالي React، وأنت تعمل عليه منفرداً.

### متى يكون Flutter أفضل فعلاً

لأكون منصفاً — Flutter يتفوّق في:

- **أداء الرسوم**: تمرير قوائم طويلة جداً وحركات معقّدة
- **اتساق العرض**: يرسم كل بكسل بنفسه، فلا اختلاف بين أندرويد و iOS
- **حجم أصغر** وبدء تشغيل أسرع

لكن تطبيقك **نماذج وقوائم وصور** — لا ألعاب ولا رسوم كثيفة. React Native
يؤدّيها بلا فرق ملموس للمستخدم.

### القرار في جملة

> Flutter أفضل لو كنت تبدأ من الصفر بلا كود سابق. أنت لا تبدأ من الصفر —
> عندك ~٢٬٥٠٠ سطر منطق مُختبَر في الميدان. React Native يحتفظ بها، Flutter
> يرميها.

### خطة عملية مقترحة

```
Expo (managed)                 بناء ونشر بلا Xcode/Android Studio
expo-router                    توجيه يشبه React Router الحالي
@supabase/supabase-js          نفس طبقة البيانات
react-native-mmkv              تخزين محلي سريع بديل localStorage
expo-image-picker + camera     الكاميرا المباشرة
expo-notifications             الإشعارات الفورية
expo-secure-store              حفظ الجلسة مشفّرة (لا localStorage)
```

**بنية مقترحة**: انقل المجلدات `config/` و `lib/` و `hooks/` كما هي إلى حزمة
مشتركة، وأعد كتابة طبقة العرض فقط. النسبة تقريباً: **٤٠٪ ينتقل، ٦٠٪ يُعاد
بناؤه بمكوّنات أصلية**.

## ٩. نقاط تستحق الانتباه أثناء البناء

| # | النقطة |
|---|---|
| ١ | `sanitizeStoragePath` إلزامية — أسماء المراكز عربية والتخزين يرفضها |
| ٢ | ترقيم مراحل الوجبة الجافة (`1` و `3`) — لا تستخدم الفهرس كمعرّف |
| ٣ | `__details` و `__photos` مفتاحان محجوزان داخل `answers` |
| ٤ | الأسئلة السلبية (`negative`) — «لا» تمنح الدرجة، وعكسها يقلب كل التقييم |
| ٥ | الأسئلة الاسترشادية (`score: 0`) لا تُحتسب في البسط ولا المقام |
| ٦ | أرقام البلاغات والطلبات من قاعدة البيانات لا من التطبيق |
| ٧ | التاريخ هجري بأرقام عربية — `extractDay('٨ ذو الحجة ١٤٤٧')` → `'8'` |
| ٨ | كل الواجهة RTL — اختبر على أندرويد و iOS، سلوكهما يختلف في الانعكاس |

## ١٠. أولوية أعلى من التطبيق

⚠️ **سياسات RLS في قاعدة البيانات مفتوحة بالكامل**: `USING (true)` للدور
`anon`. المفتاح العام سيكون داخل حزمة التطبيق — ومن يفكّك أي تطبيق يستخرجه
في دقائق.

بهذا الوضع، أي شخص يحمّل التطبيق يستطيع قراءة وتعديل وحذف بيانات كل
المستخدمين بأسمائهم وأرقام هوياتهم وجوالاتهم.

**عالج هذا قبل نشر التطبيق**، وإلا تكون قد وزّعت مفتاح قاعدة بياناتك على
المتاجر.
