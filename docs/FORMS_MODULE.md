# قسم النماذج — التصميم

آخر تحديث: 2026-08-17

---

## المشكلة

المتعهد مطالَب بنماذج رسمية: تعيين ضابط اتصال، استلام مطابخ، رفع عمال، شهادات كيروسين، وغيرها. اليوم تُدار ورقاً وواتساب، فلا أحد يعرف بدقة من سلّم ومن تأخّر — وهذا بالضبط ما يجب أن يدخل في تقييم المتعهد نهاية الموسم.

المطلوب:
- الإدارة ترفع نموذجاً وتُسنده لمتعهد أو لجميع المتعهدين بتاريخ تسليم
- المتعهد يدخل بحسابه، يشوف تنبيهاً، يعبّي، يوقّع، يسلّم
- الحالة تتحوّل تلقائياً: في الانتظار ← مُسلَّم ✓، ومتأخر إن تجاوز الموعد
- نهاية الموسم: تقرير التزام لكل متعهد

---

## القرار المحوري: من يُنشئ النماذج؟

هنا مفترق طريقين، والفرق بينهما هو الفرق بين أداة مخصّصة ومنتج قابل للبيع.

### الطريق (أ) — النماذج مكتوبة في الكود

كل نموذج ملف `src/config/forms/*.js`. سريع التنفيذ ومضبوط.
**لكن**: كل شركة حج تشتري النظام لها نماذجها الخاصة، وكل نموذج جديد يحتاج مبرمجاً ونشر إصدار. تبقى أنت عنق الزجاجة إلى الأبد.

### الطريق (ب) — بانٍ نماذج داخل النظام ← **الموصى به**

الإدارة تبني النموذج من الواجهة: تضيف حقلاً، تختار نوعه، تعلّمه مطلوباً. التعريف يُخزَّن `jsonb`، والعارض واحد عام يرسم أي نموذج.

**لماذا هذا هو الصحيح هنا تحديداً:**
- تبيع النظام لشركات مختلفة، ولكل واحدة نماذجها
- قلت «حرسلك النماذج بعدين» — مع البانٍ ترفعها بنفسك في دقائق بدل ما تنتظرني
- النموذج الجديد وسط الموسم لا يحتاج نشر إصدار
- نموذج التقييم والالتزام يعمل بنفس الطريقة في الحالتين، فلا خسارة

**التدرّج المقترح**: نبني نموذج البيانات والعارض العام أولاً، وأنا أُدخل نماذجك الأولى كبذرة من ملفاتك. البانٍ المرئي يأتي بعدها كإضافة لا كإعادة بناء — لأن الشكل الصحيح للبيانات موجود من اليوم الأول.

## البنية: ثلاث طبقات

الخلط بين هذه الثلاث هو الخطأ الشائع في أنظمة النماذج.

```
القالب       form_templates    التعريف: ما الحقول، هل يحتاج توقيعاً
  ↓          واحد لكثير
التكليف      form_assignments  «متعهد س مطالب بالنموذج ص قبل تاريخ ع»
  ↓
التسليم      البيانات المعبّأة داخل التكليف نفسه
```

القياس يقع على **التكليف** لا على القالب: نسبة التسليم، الالتزام بالموعد، سرعة الاستجابة — كلها صفات تكليف.

### الجداول

```
form_templates
  id, key, title, description, category, schema jsonb,
  requires_signature, requires_attachment, active, created_by

form_assignments
  id, season_id, template_id, caterer_id, center_id,
  due_at, assigned_by, assigned_at,
  status, submitted_at, reviewed_by, reviewed_at, review_note,
  data jsonb, attachments[], signature_url, pdf_url

form_events           -- سجل زمني: أُسند، فُتح، سُلّم، أُعيد، قُبل
  id, assignment_id, event, actor_uid, note, created_at
```

`form_events` هو ما يجيب على سؤالك «كان متجاوب ولا لا» — الاستجابة = الزمن بين الإسناد والتسليم، ولا يمكن حسابه من حقل حالة واحد.

### حالات التكليف

```
في الانتظار ──► مسودة ──► مُسلَّم ──┬──► مقبول ✓
                   ▲               └──► مُعاد للتعديل ──┐
                   └──────────────────────────────────┘

متأخر: صفة محسوبة، لا حالة مخزَّنة — «مُسلَّم ولم يُقبل بعد» و«تجاوز الموعد»
       حالتان مستقلتان، ودمجهما في عمود واحد يفقدك إحداهما.
```

## شكل تعريف النموذج

النماذج الرسمية مستندات نثرية بفراغات، لا أكوام حقول معنونة:

> نحن شركة **\_\_\_\_** سجل تجاري رقم **\_\_\_\_** نفوّض السيد/ **\_\_\_\_** هوية رقم **\_\_\_\_** للعمل ضابط اتصال...

لذلك التعريف جزآن: **بلوكات** ترسم المستند، و**سجلّ حقول** يعطي كل فراغ نوعه وقواعده.

```json
{
  "blocks": [
    { "type": "heading",   "text": "نموذج تعيين ضابط اتصال" },

    { "type": "paragraph",
      "text": "نحن شركة {{caterer_name}}، سجل تجاري رقم {{cr_number}}، نفوّض السيد/ {{officer_name}} هوية رقم {{officer_id}} للعمل ضابط اتصال لدى المركز {{center_code}} اعتباراً من {{start_date}}." },

    { "type": "fields", "columns": 2,
      "keys": ["officer_phone", "officer_email"] },

    { "type": "table",     "key": "workers" },
    { "type": "note",      "text": "يُرفق أصل الخطاب مختوماً." },
    { "type": "signature", "label": "توقيع المفوّض", "key": "signature" }
  ],

  "fields": {
    "caterer_name":  { "label": "اسم المتعهد",  "type": "text", "source": "caterer.name",      "readonly": true },
    "cr_number":     { "label": "السجل التجاري", "type": "text", "source": "caterer.cr_number", "readonly": true },
    "center_code":   { "label": "المركز",        "type": "text", "source": "center.code",       "readonly": true },
    "officer_name":  { "label": "ضابط الاتصال",  "type": "text",  "required": true },
    "officer_id":    { "label": "رقم الهوية",    "type": "id",    "required": true },
    "officer_phone": { "label": "الجوال",        "type": "phone" },
    "officer_email": { "label": "البريد",        "type": "email" },
    "start_date":    { "label": "تاريخ المباشرة","type": "date" },
    "workers":       { "label": "العمال", "type": "table",
                       "columns": [
                         { "key": "name",  "label": "الاسم" },
                         { "key": "iqama", "label": "رقم الإقامة" },
                         { "key": "job",   "label": "المهنة" }
                       ]}
  }
}
```

الرمز `{{key}}` داخل الفقرة يربط الفراغ بالسجل. نفس الحقل يظهر **داخل النص** إن ذُكر في فقرة، أو **كخانة معنونة** إن وُضع في بلوك `fields` — والاختيار للمُنشئ.

**أنواع البلوكات**: عنوان · فقرة · حقول · جدول · ملاحظة · فاصل · توقيع
**أنواع الحقول**: نص · رقم · هوية · جوال · بريد · تاريخ (هجري/ميلادي) · قائمة · اختيار متعدد · نعم/لا · ملف · جدول متكرر · توقيع

نوع **الجدول المتكرر** ليس ترفاً: «نموذج رفع العمال» جدول بطبيعته، وبدونه يصير النموذج مئة حقل مسطّح.

### التعبئة التلقائية — `source`

الحقل يقدر يسحب قيمته من سجل المتعهد أو المركز. المتعهد لا يعيد كتابة سجله التجاري ولا رقم مركزه في كل نموذج: النظام يعرفها.

هذا يقلّل الأخطاء أكثر مما يوفّر الوقت — الرقم المكتوب يدوياً عشر مرات يُكتب خطأً مرة على الأقل.

## كيف يُبنى البانٍ عملياً

الشاشة نصفان: البلوكات يميناً، وورقة A4 حيّة يساراً بترويسة الشركة وشعارها. ما تراه في المعاينة هو ما يُطبع حرفياً.

```
┌── البلوكات ──────────┐  ┌── المعاينة (A4 بهوية نصاب) ──┐
│ ▤ عنوان              │  │  [شعار نصاب]     نموذج رقم   │
│ ¶ فقرة   [+ حقل]     │  │  ─────────────────────────  │
│ ▦ حقول                │  │   نموذج تعيين ضابط اتصال    │
│ ▤ جدول               │  │                             │
│ ✎ توقيع              │  │  نحن شركة [____] سجل تجاري  │
│                      │  │  رقم [____] نفوّض السيد/     │
│ [+ إضافة بلوك]       │  │  ...                        │
└──────────────────────┘  └─────────────────────────────┘
```

**لماذا بلوكات لا محرّر نصوص غني؟** محرّر `contenteditable` في العربي RTL مصدر أعطال لا ينتهي (اتجاه المؤشر، الأرقام، اللصق من وورد)، ويحتاج مكتبة ثقيلة، ولا يترجم لـ PDF ترجمةً موثوقة. البلوكات تعطي ٩٠٪ من إحساس المستند، وتقابل الـ PDF واحداً بواحد، وتشتغل في RTL بلا مفاجآت.

**إدراج حقل داخل النص**: المُنشئ يكتب الفقرة ويضغط «+ حقل» فيُدرَج `{{key}}` عند المؤشر، ويظهر في المعاينة فوراً كفراغ منقّط. لا يكتب أقواساً بيده.

### الهوية والترويسة

الترويسة والتذييل ليسا جزءاً من النموذج — يأتيان من `src/config/brand.js`. أي نموذج يُطبع بشعار الشركة واسمها ورقم مرجعي وتاريخ هجري/ميلادي وترقيم صفحات.

نتيجة ذلك: **بيع النظام لشركة أخرى = تبديل `brand.js`**، فتخرج كل نماذجها بهويتها هي دون لمس نموذج واحد.

البنية موجودة بالفعل في `AdminReportGenerator.jsx` — jsPDF مع خط Cairo مضمّن ومُشكّل عربي يدوي. تُستخرج إلى `src/lib/pdf/document.js` ليستعملها الجميع.

### نماذج جاهزة

النماذج المتعارف عليها تُشحن كبذرة `form_templates` مع النظام، ويقدر العميل ينسخ أياً منها ويعدّله بدل أن يبدأ من ورقة بيضاء.

## بوابة المتعهد

مساران منفصلان تماماً عن لوحة الإدارة:

```
/caterer/home      نماذجي · المطلوب الآن · المتأخر
/caterer/form/:id  تعبئة وتوقيع وتسليم
/caterer/alerts    التنبيهات
```

يتطلب:
- دور جديد `caterer` في `users`
- عمود `caterer_id` على `users` يربط الحساب بالشركة
- `RequireCaterer` بجانب `RequireAuth` و`RequireAdmin` القائمين

الواجهة مبسّطة عمداً: المتعهد ليس مستخدماً محترفاً للنظام، ويدخل بضع مرات في الموسم. شاشته الأولى يجب أن تجيب سؤالاً واحداً — **ما المطلوب مني الآن؟**

## التوقيع

ثلاث طرق، والصحيح دعم الثنتين الأخيرتين معاً:

| الطريقة | ملاحظة |
|---|---|
| توقيع بالإصبع على الشاشة | سريع، لكن لا يُغني عن الورق المختوم رسمياً |
| رفع نسخة موقّعة ومختومة | ما تحتاجه الجهات فعلاً |
| **كلاهما** | يوقّع إلكترونياً للإقرار، ويرفق المختومة للأرشيف |

بعد التسليم يُولَّد **مستند بترويسة نصاب** يجمع البيانات والتوقيع — والبنية جاهزة في `AdminReportGenerator.jsx` (خط Cairo مضمّن ومُشكّل عربي).

## قياس الالتزام — الهدف النهائي

لكل متعهد في كل موسم:

| المؤشر | الحساب |
|---|---|
| نسبة التسليم | مُسلَّم ÷ مُسنَد |
| الالتزام بالموعد | سُلّم قبل الموعد ÷ مُسلَّم |
| متوسط التأخير | بالأيام، للمتأخرات فقط |
| سرعة الاستجابة | وسيط الساعات من الإسناد إلى التسليم |
| جودة التعبئة | عدد المُعاد للتعديل |

هذه الخمسة تُغذّي مباشرةً نطاقات **أخضر / أصفر / أحمر** في المرحلة ٤، وتجيب سؤالك: «هل كان متجاوباً ويسلّم في الوقت؟» — برقم، لا بانطباع.

## قرارات مطلوبة قبل البدء

1. **الطريق (أ) أم (ب)؟** — التوصية: (ب)
2. **كيف يسجّل المتعهد دخوله؟** — رقم الهوية كالمراقبين، أم بريد وكلمة مرور كالموظفين؟
3. **حساب واحد للشركة أم حساب لكل ضابط اتصال؟** — الواحد أبسط، والمتعدد يعطيك «من سلّم» بالاسم
